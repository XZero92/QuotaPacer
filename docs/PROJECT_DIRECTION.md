# QuotaPacer 프로젝트 방향성

## 문서 목적

이 문서는 QuotaPacer의 제품 정체성, 장기 방향과 변경 시 지켜야 할 경계를 기록합니다. 새로운 작업 세션은 구현에 착수하기 전에 이 문서를 읽고, 아래 구분에 따라 판단합니다.

- **현재 구현**: 지금 소스에서 동작하며 테스트할 수 있는 기능
- **확정 원칙**: 이후 구현에서도 특별한 재논의 없이 유지할 결정
- **예정 기능**: 방향은 확정됐지만 세부 설계와 구현이 남은 기능
- **미결정 사항**: 사용자 결정이나 별도 설계가 필요한 내용

현재 동작에 관해서는 실제 소스와 테스트가 최종 기준이며, 설치·개발 명령은 [README](../README.md)를 따릅니다. 이 문서와 구현이 어긋나면 차이를 숨기지 말고 문서 또는 구현 중 어느 쪽을 변경할지 명시적으로 판단합니다.

## 제품 정의

QuotaPacer는 Codex 사용량을 화면 위의 작은 오버레이로 보여주고, 사용자가 주어진 제한 주기 안에서 사용 페이스를 조절하도록 돕는 크로스 플랫폼 데스크톱 보조 도구입니다.

핵심 가치는 단순히 현재 백분율을 보여주는 데서 끝나지 않습니다. 장기적으로는 현재 소비 속도가 재설정 시점까지 지속 가능한지 판단하고, 사용자가 정한 일일·요일별 기준에서 벗어날 때 조용하고 이해하기 쉬운 신호를 제공하는 것이 목표입니다.

### 정체성 경계

- 제품명은 **QuotaPacer**입니다.
- OpenAI 또는 Codex의 공식 앱이나 공식 기능으로 보이게 하지 않습니다.
- Codex Desktop App을 대체하거나 수정하는 도구가 아니라, 별도로 실행되는 비공식 보조 도구입니다.
- `Token` 소비량 측정기가 아닙니다. app-server가 제공하는 계정별 rate-limit 사용률과 제한 창을 표시합니다.
- Pet·캐릭터 기능은 가까운 로드맵에 포함하지 않습니다. 향후 가능성을 막지는 않지만 제품 구조와 명칭을 이를 전제로 설계하지 않습니다.

## 제품 원칙

### 1. 한눈에 이해할 수 있어야 한다

기본 크기에서는 가장 중요한 제한 창 하나와 남은 비율만 짧게 보여줍니다. 사용자가 작업 흐름을 멈추지 않고 상태를 파악할 수 있어야 하며, 여러 창과 페이스 정보는 사용자가 큰 크기를 선택했을 때 표시합니다.

### 2. 표시보다 페이스 조절을 지향한다

현재 MVP는 사용량 표시기이지만, 후속 기능의 판단 기준은 “이 기능이 사용자가 재설정 시점까지 사용량을 배분하는 데 도움이 되는가”입니다. 단순한 수치·차트 추가보다 예측 가능한 경고와 행동 가능한 설명을 우선합니다.

### 3. 이동은 기본 조작, 메뉴는 보조 조작이다

오버레이 본체의 왼쪽 드래그는 위치 이동을 우선합니다. 크기 변경과 새로고침 같은 보조 조작은 우클릭 메뉴와 트레이에서 제공하며, 항상 보이는 조작 버튼이 핵심 정보를 밀어내지 않게 합니다.

### 4. 조용하지만 신뢰할 수 있어야 한다

항상 위 오버레이가 사용자의 시선을 과도하게 빼앗지 않아야 합니다. 오류가 발생하면 마지막 성공 값을 보존하면서 지연 상태를 분명히 알리고, 값이 없는 상황을 임의의 0%나 100%로 꾸미지 않습니다.

### 5. 계정 응답을 있는 그대로 존중한다

문서화된 일반 정책보다 현재 계정의 app-server 응답을 UI의 권위 있는 데이터로 사용합니다. 존재하지 않는 제한 창을 예상해 빈 행이나 경고를 만들지 않습니다.

## 현재 구현 기준선

현재 버전은 `Tauri 2 + React + TypeScript + Rust` 구조의 데스크톱 앱입니다.

### 오버레이

- 투명하고 프레임이 없으며 항상 위에 표시되는 세 가지 정보 밀도 모드
- `small`은 152×56 캡슐 안의 원형 게이지와 대표 창의 기간·남은 비율 표시
- `middle`은 280×72 캡슐에 대표 창의 바 게이지와 리셋 정보 표시
- `large`는 360px 폭 카드에 실제로 반환된 모든 제한 창의 상태 판정, 계획 비교 bullet gauge와 현재부터 초기화까지의 forecast timeline 표시
- `large` 높이는 단일 창 240px, 추가 창당 176px, 최대 520px이며 이후 내부 스크롤 사용
- 본체 드래그를 통한 창 이동과 위치 저장
- 우클릭 메뉴와 트레이에서 크기 변경, 페이스 설정, 새로고침, CLI 경로 선택, 숨기기와 종료 제공
- 여러 제한 창은 필요하면 내부 스크롤하되 스크롤 바는 시각적으로 숨김
- 저장 위치가 현재 모니터 작업 영역을 벗어나면 실행 시 보정

### 사용량 연동

- 사용자가 설치하고 로그인한 Codex CLI를 필수 실행 환경으로 사용
- `codex app-server --stdio`와 JSONL RPC로 통신
- `initialize` → `initialized` → `account/read` → `account/rateLimits/read` 순서로 초기화
- `account/rateLimits/updated` 이후 전체 스냅샷 재조회
- 60초 주기 갱신과 프로세스 종료 시 재연결
- CLI 버전 숫자보다 실제 app-server 초기화와 필수 메서드 성공 여부로 호환성 판정

### 표시 규칙

- `rateLimitsByLimitId`가 있으면 우선 사용하고, 비어 있으면 단일 `rateLimits`로 대체
- 각 bucket의 `primary`와 `secondary`를 독립된 제한 창으로 취급하며 null은 생략
- `primary = 5시간`, `secondary = 주간` 같은 의미를 고정하지 않음
- 300분은 `5시간`, 10080분은 `주간`, 다른 값은 실제 지속시간으로 동적 표기
- 대표 창은 남은 비율이 가장 낮은 창으로 선택
- 동률이면 빠른 리셋, 짧은 지속시간, ID 사전순으로 선택
- 남은 비율이 50% 초과면 기본색, 20~50%면 주의색, 20% 미만이면 위험색
- 최근 같은 제한 창 세대의 관측이 6시간 이상이면 최대 24시간 속도로, 부족하면 제한 시작 이후 기간 평균으로 소진 시각을 예측
- 정확히 7일인 창에는 균등 또는 사용자가 지정한 요일별 배분 계획을 적용하고, 그 외 창에는 기간 경과율을 권장선으로 사용
- 계획보다 1%p 넘는 상태와 초기화 전 소진 위험은 연속 두 번 확인한 뒤 OS 알림 대상으로 확정
- stale 상태에서는 기존 판정을 유지하고 새 OS 알림을 보내지 않음
- pace 계산에 필요한 기간·리셋·기준 시각이 없으면 임의 값을 만들지 않고 계산 불가로 표시
- 인증됐지만 제한 창이 없으면 `no_limits`로 표시하고 가짜 백분율을 생성하지 않음
- 주간 창 하나만 반환되는 응답을 정상적인 단일 창 상태로 취급

## 확정된 기술·보안 원칙

### Codex CLI를 필수로 유지한다

일반 사용자가 Codex Desktop App만 설치했을 가능성은 인정하지만, 앱 패키지 내부 실행 파일이나 비공개 인증 저장소에 의존하지 않습니다. 관리자 권한으로 접근 제한을 우회하는 방식도 사용하지 않습니다.

CLI 탐지 순서는 다음과 같습니다.

1. 사용자가 저장한 실행 파일 경로
2. `CODEX_CLI_PATH`
3. 현재 프로세스의 `PATH`
4. Windows `where.exe` 또는 Unix 로그인 셸

Windows에서는 네이티브 `.exe`와 npm의 `.cmd`·`.bat`, PowerShell `.ps1` 래퍼를 지원합니다.

### 인증 정보에 직접 접근하지 않는다

- Codex 인증 토큰과 계정 이메일을 읽거나 전달하지 않습니다.
- 앱 내부 로그인 기능을 만들지 않습니다.
- API Key 인증을 ChatGPT 계정 사용량 조회로 오인하지 않습니다.
- `account/read`의 계정 유형은 인증 가능 여부 판단에만 사용합니다.
- 계정과 rate-limit bucket의 `planType` 불일치는 오류로 취급하지 않습니다.

### 저장을 최소화한다

디스크에는 사용자가 선택한 CLI 경로, 오버레이 크기·위치, 페이스 설정과 예측에 필요한 최대 25시간의 최소 이력을 저장합니다. 단기 이력은 관측 시각·제한 창 식별자·리셋 시각·사용률과 알림 중복 방지 상태만 포함하며, 설정 창에서 즉시 삭제할 수 있습니다. 인증 토큰과 계정 이메일은 저장하지 않습니다.

### 프로토콜 변화를 격리한다

app-server 요청·응답 차이는 Rust 어댑터에 모읍니다. React UI가 `primary`, `secondary` 또는 특정 CLI 버전의 원시 JSON 형태에 직접 의존하지 않도록 정규화된 `UsageViewState`를 경계로 유지합니다.

## UX 방향

### 오버레이 크기

사용자는 다음 세 레이아웃을 선택할 수 있습니다.

- `small`: 캡슐 안의 원형 게이지와 대표 창의 기간·남은 비율 표시
- `middle`: 대표 창의 이름·수치·바 게이지·리셋 상태 표시
- `large`: 모든 실제 제한 창의 지속 가능 판정, 실제 사용률과 현재 권장선을 비교하는 bullet gauge, 예상 소진 시점과 초기화를 비교하는 timeline 표시

`small`, `middle`, `large`는 단순 배율이 아니라 정보 밀도와 레이아웃이 다른 모드입니다. 크기 모드는 우클릭 메뉴와 트레이에서 선택하며 디스크에 저장합니다.

### 투명도와 형태

- 오버레이 표면 바깥에 WebView 배경이 보이지 않아야 합니다.
- 스크롤이 필요하더라도 데스크톱 오버레이에 눈에 띄는 기본 스크롤 바를 노출하지 않습니다.

### 상태와 오류

- 마지막 성공 값이 있으면 오류 중에도 값을 유지하고 업데이트 지연 시간을 표시합니다.
- CLI 미설치, 권장 버전 미달, 로그인 필요, 지원하지 않는 인증과 일반 오류를 구분합니다.
- 오류 메시지는 사용자가 다음 행동을 알 수 있게 쓰되, 지원하지 않는 우회 방법을 제안하지 않습니다.

### 페이스 경고와 설정

- 계획 초과와 초기화 전 소진 위험은 Large의 문구와 색상으로 항상 표시합니다.
- 실제 사용량은 기본색, 계획선 초과 구간은 주의색, 신뢰 가능한 초기화 전 소진 위험은 위험색으로 역할을 분리합니다.
- 초기 추정 소진 가능성은 주의색으로 표시하고, 충분한 관측 뒤 신뢰 기준을 충족하면 위험색으로 승격합니다.
- stale 상태는 마지막 값을 흐리게 만들지 않고 지연 문구로 구분합니다.
- OS 알림은 기본적으로 꺼져 있으며 설정 창에서 사용자가 직접 켤 때만 권한을 요청합니다.
- 7일 창은 기본 1/7 균등 배분 또는 합계 100±0.1%인 월~일 사용자 배분을 사용합니다.
- OS 알림은 제한 창 세대·경고 종류별 한 번만 보내며 두 경고가 동시에 확정되면 결합합니다.
- Large는 최근 관측 시간 또는 기간 평균·초기 추정 배지를 함께 보여 예측 근거를 숨기지 않습니다.
- Line chart는 현재 Large에 포함하지 않습니다. 제한 창 전체 이력과 전용 공간을 갖춘 추세 상세 기능이 필요해질 때 별도로 검토합니다.

## 비목표와 가까운 범위에서 제외할 항목

- Codex CLI 번들링
- 앱 내부 Codex 로그인
- 인증 토큰 또는 Desktop App 내부 파일 직접 접근
- 관리자 권한을 이용한 접근 제한 우회
- 크레딧 구매나 결제 기능
- 공식 Codex 앱처럼 보이는 브랜딩
- 사용 목적이 불명확한 장기 사용량 수집과 분석 대시보드
- Pet·캐릭터 애니메이션
- 자동 시작

비목표는 영구 금지 목록이 아니라 현재 제품 목적을 흐리지 않기 위한 경계입니다. 추가하려면 사용자 가치, 개인정보 영향, 크로스 플랫폼 비용과 기존 원칙에 미치는 영향을 먼저 검토합니다.

## 미결정 사항

다음 항목은 새 세션이 임의로 확정하지 않습니다.

- 방해 금지 시간이나 알림 시간대 설정
- 25시간을 넘는 장기 이력·추세 차트 도입 여부
- macOS 배포 경로와 Mac App Store 대응 여부
- Linux X11·Wayland별 지원 수준과 배포 형식

## 변경 판단 기준

새 기능이나 구조 변경을 제안할 때 다음 질문에 답합니다.

1. 사용자가 남은 사용량과 지속 가능한 페이스를 더 빨리 이해할 수 있는가?
2. app-server가 반환하지 않은 의미를 추측하거나 하드코딩하지 않는가?
3. 인증 정보와 사용 이력을 불필요하게 읽거나 저장하지 않는가?
4. 드래그 우선의 조용한 오버레이 경험을 해치지 않는가?
5. Windows, macOS, Linux에서 구현 가능한가? 차이가 있다면 명확히 격리했는가?
6. 단일 주간 창, 여러 제한 창, 빈 제한 창과 stale 상태를 회귀 테스트했는가?

## 완료 기준

동작 변경은 관련 프런트엔드 또는 Rust 테스트와 함께 제출합니다. 최소한 변경 범위에 해당하는 타입 검사, Lint, 테스트, Rustfmt와 Clippy를 통과해야 합니다. 창 투명도, 드래그, 다중 모니터·DPI, X11·Wayland처럼 자동화가 어려운 항목은 수동 검증 범위와 결과를 기록합니다.
